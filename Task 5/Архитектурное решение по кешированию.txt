1. Мотивация
    - Низкая скорость работы UI операторов: Загрузка дашборда с заказами занимает много времени
    - Длительный расчет стоимости: Клиенты ждут 2-30 минут для получения цены
    - Рост нагрузки: ~ +100 заказов/месяц → увеличение запросов 

Цели, которые можно и нужно достичь при использовании кеширования
    - Ускорение загрузки дашборда для операторов 
    - Сократить время расчета стоимости заказам
    - Снизить нагрузку на БД MES 

2. Предлагаемое решение

Будем использовать серверное кеширование через Redis.
Почему выбран данный тип кеширования:
    - Данные по заказам динамические и используются множеством операторов
    - Сложные агрегации трудно вынести на клиентский уровень
    - Требуется централизованное управление инвалидацией, чтобы избежать чтения устаревших данных. Т.к. от актуальности данных о Заказах зависит ЗП операторов.

Для реалиизации выберем Cashe-Aside паттерн. Данный паттерн прост в реализации, эффективен для тяжелых запросов на чтение данных и позволяет гибко управлять инвалидацей.

Если сравнивать с Write-Through и Refresh-Ahead, то:

    - Write-Through: Сложен для синхронизации, замедляет запись в данные.
    - Refresh-Ahead: Появляется риск получения устаревших даннных


Чтение списка заказов на диаграмме в директории Task5 "Диаграмма последовательности кеширования для дашборда с заказами.puml" (есть скриншот диаграммы "Кеширование чтения заказов.png" ) :

    - Оператор запрашивает список заказов в работе
    - Система проверяет наличие данных в Redis:
        - При попадании: немедленный возврат из кеша
        - При промахе: запрос к БД → сохранение в кеш → возврат данных
    - TTL=30 секунд защищает от устаревания данных



Изменение статуса на диаграмме в директории Task5 "Диаграмма последовательности кеширования для дашборда с заказами (Инвалидация кеша).puml" (есть скриншот диаграммы "Кеширование обновлениия статуса заказов.png" ) :

    - Оператор обновляет статус заказа
    - Система обновляет данные в БД
    - Инвалидируются все зависимые ключи:
        - Фильтр по статусу
        - Конкретный заказ по id
    - Гарантируется актуальность данных при следующем чтении


Стратегии инвалидации, которые будем применять:
    - Программная инвалидация. Применяется при изменении статуса заказа и обновлении данных о заказе. Гарантирует, что будет показана актуальная информация о Заказах.
    - Временная инвалидация. Страхует от неактуальных данных о заказах за счет TTL.

Не подходят (по моему мнению):
     - Инвалидация на основе изменений.  Риск показа устаревших данных операторам в критических статусах 
     - Инвалидация по ключу. Проста в реализации, но не будет работать с агрегированными данными по статусам заказа.
     - Инвалидация, основанная на запросах. Очень высокая сложность реализации вследствии чего высокие трудозатраты на поддержку.

Вывод:  Для производственной системы MES с высокими требованиями к точности данных комбинированный подход Программной и временной инвалидаций довольно стабильное и относительно нетрудоемкое решение.
