1. Идентификация существующих и потенциальных проблемных мест:

1.1 Критическая нагрузка на MES

- Довольно медленный расчет стоимости: 2-30 минут на расчет блокирует ресурсы.

- Медленный UI (Дашборд): Проблемы с загрузкой первой страницы даже после пагинации/фильтров указывают на неоптимизированные запросы к БД PostgreSQL (отсутствие индексов, неоптимальный план запросов и тп) или недостаточность ресурсов инстанса.

- Единый инстанс: Нет горизонтального масштабирования. Весь расчет и UI обслуживаются одной нодой.

- Потенциал: Расчет стоимости – идеальный кандидат для асинхронной обработки и горизонтального масштабирования.

1.2 Ненадежная интеграция между MES и CRM через RabbitMQ (Потеря заказов):

- Отсутствие Dead Letter Queues (DLQ): Нет механизма обработки "отравленных" или постоянно необрабатываемых сообщений.

- Отсутствие Retry Policies: Нет стратегии повторных попыток доставки при временных сбоях.

- Отсутствие трейсинга: Трудно отследить жизненный цикл сообщения (заказа) через системы

1.3. Текущая инфраструктура не готова к росту нагрузки:

- Single Point of Failure (SPOF) везде: Один инстанс приложения и один инстанс БД  для каждой системы. Выход из строя приложения или БД порождает полную недоступность любой из трех систем (Интернет магазин/CRM/MES).

- Отсутствие масштабирования БД: Нет реплик для чтения, шардинга. БД MES – главное узкое место для UI и расчетов стоимости заказов.

- Ручное масштабирование: Инфраструктура не адаптируется под нагрузку автоматически.

- Любой пик нагрузки (особенно от API) ведет к деградации или отказу.

- Отсутствие мониторингов критических метрик.

1.4 Проблемы с процессами разработки и релизов:

- Ручное тестирование на high/highest багах: Главная причина задержек релизов. Нет автоматизации E2E.

- Ручной деплой в release/prod: Риск человеческой ошибки, медленная реакция на фиксы.

- Двухнедельные спринты с месячными задержками: Процесс неэффективен. Тестирование – bottleneck.

- Неспособность быстро доставлять на prod исправления и новые фичи усугубляет бизнес-проблемы.

1.5 Архитектурная связность и монолитность:

- MES как монолит: Расчет стоимости, управление производством, дашборд – тесно связаны. Проблема в одном компоненте влияет на все.

- Жесткая связь статусов: Сквозная cтатусная модель заказа проходит через три разные системы. Если потребуется изменить процесс, то это будет очень сложно реализовать.

- Трудно развивать отдельные части системы независимо.

1.6 Кадровые проблемы:

- Нехватка экспертизы: Один C# разработчик на критичный механизм - MES. Ограниченные знания React (фронт MES). QA без глубокой автоматизации.

- DevOps перегружен: Один человек на всю инфраструктуру и CI/CD.

2. Инициативы, которые необходимы для устранения нежелательных ситуаций

2.1. Оптимизация MES (UI, расчет стоимости заказа):

- UI: Глубокий анализ запросов дашборда, добавление индексов, денормализация, кэширование (Redis), выделение read-only реплики БД для UI.

- Расчет стоимости изделия: Оптимизация алгоритма расчета (параллелизм, упрощение связи между стоиимостью и моделью изделия, внедрение ИИ инструментов).

2.2. Обеспечение надежности RabbitMQ:

- Настроить Retry Policies и создать Dead Letter Queues (DLQ) и процесс их обработки/алертинга.

- Внедрить базовый трейсинг сообщений.

2.3. Устранение Single Point of Failure (SPOF) и базовое масштабирование:

- Внедрить реплики БД для чтения (MES и CRM).

- Рассмотреть возможность размещения БД в кластере (например, YDB для MES).

- Настроить балансировщики нагрузки (Load Balancer) перед приложениями.

- Подготовить шаблоны/скрипты для быстрого запуска дополнительных инстансов приложений (на первом этапе ручное масштабирование).

- Добавить мониторинги по методу USE/RED для анализа производительности систем.

- Реализовать системы логирования для каждого из сервисов.

2.4. Автоматизация тестирования и CI/CD:

- Приоритет: Создание набора E2E тестов для критических сценариев (создание заказа через магазин, расчет стоимости, изменение статуса через CRM/MES).

- Интеграция E2E тестов в CI/CD пайплайн (запуск на dev/release).

- Автоматизация деплоя в release/prod окружение (после прохождения тестов).

2.5. Рефакторинг MES в сторону сервисной архитектуры:

- Выделение отдельного сервиса Расчетов Стоимости (CalculatePricingService): Отделить расчет стоимости в независимый сервис (возможно, на .NET Core для кроссплатформенности). Создать для него отдельную очередь. 
За счет данного рефакторинга можно будет формировать несклько инстансов данного сервиса при повышении нагрузок.

- Продумать вариант, когда весь процесс заказа можно реализовать через асинхронную модель с учетом точек отката по статусам заказа.

2.6 Усиление команды:

- Backend C# Developer. Обоснование: Один C# разработчик на критичный механизм для поддержки и рефакторинга MES скорее всего перегружен задачами и масштабировать MES в отдельный сервис и добавлять новые фичи у него не получится.

- QA Automation Engineer. Обоснование: Ключевая роль для улучшения релизов и повышения качества "выкатки" обновлений. Существующий ручной тестировщик может тоже начать обучаться у нового сотрудника.

- DevOps Engineer. Для реализации отказоустойчивости, автоматизации масштабирования, улучшения CI/CD в помощь единственному DevOps, который есть на текущий момент.

3. Приоритезация инициатив

Критерии приоритезации:

- Остановить бизнес-потери. Потеря заказов, уход клиентов/партнеров.

- Стабилизировать основную систему (MES).

- Улучшить процесс доставки. Позволить команде быстро выпускать исправления и улучшения.

- Заложить основу для масштабируемости (потенциальный переход на микросервисную архитектуру).

- Усиление команды.

Ниже привожу перечень приоритетных задач (от высокого к более низкому):

1) Добавиить мониторинги на критические узлы систем. Детализации по мониторингам расписаны в файле "Выбор и настройка мониторинга в системме" (директория Task 2)

2) Обеспечение надежности RabbitMQ. Поскольку на мой взгляд это прямая 2ричина потери части заказов (бизнес теряет и деньги и репутацию).
Реализация базовых гарантий доставки RabbitMQ (Ack/Nack) и обработки ошибок (Retry, DLQ) — это конфигурация и небольшие изменения кода в потребителях (CRM и MES). Не требует переделки архитектуры.
Без надежной доставки сообщений последующие улучшения не имеют большого "выхлопа".

2) Оптимизация софта MES. UI дашборды и вывод отдельного сервиса расчета стоимости.
UI:
- Медленный UI напрямую снижает эффективность производства и мотивацию ключевых сотрудников (операторы).

- Необходимо профилировать запросы из UI, т.е. выявить медленные запросы к БД. Затем необходимо оптимизировать БД, а именно добавить недостающие индексы,
рассмотреть денормализацию или материализованные представления для часто запрашиваемых агрегаций по статусам.

- Также можно внедрить кеширование (например Redis) Кэшировать результаты сложных запросов дашборда (например, кол-во заказов по статусам) на короткий срок 1-5 минут.

MES:

- Реализовать асинхронный сервис расчета стоимости заказа. 
Например при получении заказа (SUBMITTED) магазин отправляет сообщение в новую очередь price_calculation_requests (RabbitMQ). Статус заказа меняется на PRICE_PENDING.
Отдельный worker внутри MES (в дальнейшем отдельный сервис расчета стоимости заказа) будет подписан на очередь price_calculation_requests и работать в фоне, никоим образом не мешая работе в UI MES.
После расчета стоимости заказа worker отдаст сообщение в отдельную очередь price_calculation_result, на которую подписаны онлайн магазин/CRM. И уже магазин/CRM слушая очередь price_calculation_result будут получать 
информацию о том рассчитана ли стоимости или же произошла ошибка в момент расчета.

3) Автоматизировать тестирование.
Ручное тестирование — одна из причин месячных задержек релизов.

Соответственно необходимо развивать компетенции в автотестировании.
Автоматический деплой в release снижает риск человеческой ошибки и ускоряет финальную проверку доработок перед "выкаткой" в prod.

4) Устранить единую точку отказа в сервисах и реализовать базовое масштабирование.
Реплицировать БД, добавить балансировщик нагрузки, реализовать шаблоны инстансов систем (как минимум для быстрого ручного развертывания в случае "падений" систем)

5) Усилить команду в формате описанном в п.2.6

*Пункты 1, 2 и 4 я бы и выбрал как приоритетные для реализации в первом полугодии.

Целевая Архитектура через 6 Месяцев:

1. Надежная асинхронная коммуникация между сервисами.
- Все интеграции между Магазином, CRM, MES и новыми сервисами используют асинхронные очереди RabbitMQ с гарантиями доставки (Ack/Nack, Retry, DLQ, мониторинг).
2. Декомпозиция монолитного софта MES. Вывод расчетов стоимости заказа в отдельный сервис. Сам MES будет фокусиироваться на управлении статусами, задачами операторов, логистикой и т.п.
3. Масштабируемая инфраструктура:
    3.1. Балансировщики нагрузки перед каждым прииложением (Магазин/CRM/MES)
    3.2. Реплицированные БД
    3.3  Мониторинги. Можно использовать Prometheus/Grafana для отслеживания ключевых метрик приложений, БД, очередей, инфраструктуры. Настроены алерты на критические ошибки.
4. Более гибкий процесс разработки и доставки обновлений.
    4.1. Автоматиизированные E2E тесты
    4.2. Автоматический деплой после тестов на dev/release среды
5. Началось усиление команды. Как минимум был нанят еще один C# разрабочик для работы с MES.

Естественно, что за полгода система не станет идеальной, но уже будет более стабильно работать в отличии от текущей ситуации.
