1. Точки риска для покрытия трейсами:

    - Интеграция через RabbitMQ. Потеря сообщений между системами, особенно при переходе статусов SUBMITTED (интернет магазин)-> PRICE_CALCULATED (MES)
    - Расчет стоимости в MES. Долгие расчеты (=>30 мин) без видимости прогресса.
    - Зависание на переходе статуса заказа MANUFACTURING_APPROVED (CRM) -> MANUFACTURING_STARTED (MES)
    - API для партнеров. Отсутствие трейсинга внешних запросов

Системы для покрытия трейсингом (названия из):
Internet Shop (Shop API)
CRM (CRM API)
MES (MES API)
RabbitMQ

Данные для трейсов :
trace_id - можно использовать GUID заказа
span_id - id этапа обработки заказа 
service_name - имя сервиса, который обрабатывает заказ
operation - название текущего этапа процесса, например выполняемый метод API 
start_time  - начало обработки
end_time  - окончание обработки
status - статус выполнения обработки
error_code - код ошибки
order_id - идентификатор Заказа 
user_id - идентикифатор клиента на стороне интернет-магазина 
partner_id - идентификатор партнера при использовании API для партнеров
metadata - JSON модель остальных технических атрибутов для понимания контекста


2. Мотивация 

Техническая мотивация:
     - Сокращение времени диагностики инцидентов 
     - Выявление скрытых узких мест , например зависаний в разборе очереди RabbitMQ
     - Упрощение интеграций между системами

Бизнес мотивация:     
    - Снижение потерь заказов через предотвращение зависаний
    - Увеличение лояльнности от партнеров и клиентов
    - Потенциальное сокращение расходов на поддержку


3.  Предлагаемое решение

    - Ссылка на схему: Схема трейсинга для 'Александрит'.drawio
    
Инструментация приложений:
    - Интернет магазин и CRM: OpenTelemetry Java Agent + Spring Boot Starter
    - MES: OpenTelemetry .NET SDK
    - RabbitMQ: amq.rabbitmq.trace -  специальный обменник, который используется для трассировки сообщений. Он является частью RabbitMQ по умолчанию.

Развертывание бэкенда для трейсов:
    - Managed Elasticsearch в Yandex Cloud
    - Jaeger All-in-One для dev-среды
    - Jaeger Production Cluster (Collector + Query + UI) для prod

Также можно развернуть, например, Telegram-бот для поиска трейсов через фильтрацию по бизнесовому идентификатору Заказа (order_id), чтобы по запросу выстраивалась цепочка трейсов и было понимание, что происходит с заказом с мобильного телефона в любой момент. 
Пример использования бота: партнер спрашивает у нашего менеджера, что с Заказом и передает менеджеру его идентификатор. Сотрудник (разработчик/продуковнер/тимлид), имеющий доступ к функционалу бота, с телефона по order_id может понять, на каком этапе находится заказ.


4. Компромиссы

Случаи, где трейсинг неэффективен или дорог:
    - По исходным данным MES куплен с исходным кодом, но мы не знаем на какой версии .net и версии С# он написан. Если кодовая база на старой версии С#, то может не быть поддержки современных библиотек и нужно будет много времени для адаптации сервиса к 
    современным методам разработкии.
    - Высоконагруженные эндпоинты. Например трейсинг расчета 3D-моделей в MES.
    - Тоже самое как и в случае с MES может быть с Интернет магазином и CRM (устаревшие версии Spring Boot)
    
Трейсинг будет эффективен для:
    - Сквозного отслеживания заказов от создания до передачи в производство
    - Диагностики потерь сообщений между системами
    - Анализа задержек в ключевых интеграционных точках    

5. Безопасность 

Поскольку трейсы могут содержать конфиденциальные данные (номера заказов, пользовательские метаданные), передаваемые между сервисами и Jaeger, то необходимы меры для защиты этих данных.

5.1. Использовать защищенный канал передачи данных от сервисов к Jaeger, например передавать данные по gRPS и использовать TLS версии 1.3
5.2. Доступ к Jaeger давать только через whitelist ip адресов наших сервисов
5.3. К Jaeger UI выдать доступ только команде разработки    
5.3  Добавить хэширование для данных 
5.4  Создать регламент по хранению данных трейсов, чтобы старые трейсы не копились на серверах.
