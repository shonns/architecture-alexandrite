1. Какие логи нужно собирать на первичном этапе улучшений систем:

    - Интеграции RabbitMQ - точки потери сообщений

    - Переходы статусов заказа - моменты зависаний

    - Расчет стоимости заказа - длительные операции

    - API для партнеров - входная точка партнерских заказов


Список логов уровня INFO:

Интернет магазин. Загрузка 3D-модели украшений. Логируем: текущее время, id клиента, размер файла, время загрузки 
Расчет стоимости украшения (MES). Запуск и завершение расчета стоимости. Логируем: время начала расчета, время окончания расчета, id Заказа, статус расчета (выполнен или ошибка).
CRM. Изменение статуса заказа. Логируем: текущее время, id Заказа,  предыдущий статус, новый статус
RabbitMQ. Доставка сообщений. Логируем: текущее время, id сообщения, название очереди, статус сообщения (доставлено, отклонено)

Но если обобщить, то логировать нужно критически важные места, которые влияют на прохождение "воронки" Заказа.

Можно добавить еще уровни логирований, например:

TRACE и DEBUG  - для отладки в среде разработки (dev)

WARN - для критических ситуаций, например если по какой-то причине произошла повторная обработка одно и того же Заказа.

ERROR - критический сбой, например произошла ошибка в момент перехода статуса Заказа 

FATAL - когда перестает работать какой-либо из сервисов (например стал недоступен MES для партнеров по API)


2. Мотивация

- Возможность реконструировать события на основе логов, что позволит снизить, например, потерянные Заказы, на что жалуются партнеры.
- Будет больше данных для анализа производительности узких мест, например, долгий расчет стоимости Заказа. Что приведет к большей лояльности партнеров и внешних клиентово. 
- Скорее всего уменьшиться время диагностики инцидентов, что позволит высвободить время команды разработки.

Приоритеты для реализации логирования:

1. MES и RabbiqMQ. Т.к. потеря заказов скорее всего происходит на этом уровне.
2. API для партнеров. Т.к. партнеры жалуются.
3. Сервис расчета стоимости. Возможно долгий срок расчета связан не только с кол-вом полигонов в 3D модели.
4. Онлайн-магазин. Клиенты ведь тоже жалуются.

Технические метрики, на которые может положительно повлиять внедрение логирования:
    - Меньше багов в релизах
    - Улучшение latency для API
    - Уменьшение MTTR (Mean Time To Repair)

Бизнес-метрики, на которые может положительно повлиять внедрение логирования:
    - Увеличение NPS клиентов
    - Уменьшение простоев для операторов
    - Увеличение конверсии по партнерскому API


Вывод: За счет сбора логов работа всех интеграций между 3мя системами станет более прозрачной и доступной к анализу проблем, что даст больше времени на доработку и масштабируемость всей сервисной инфраструктуры "Александрит".


3. Предлагаемое решение
Схема:  https://github.com/shonns/architecture-alexandrite/blob/architecture-alexandrite/Task%204/%D0%A1%D1%85%D0%B5%D0%BC%D0%B0%20%D1%82%D1%80%D0%B5%D0%B9%D1%81%D0%B8%D0%BD%D0%B3%D0%B0%20%D0%B8%20%D0%BB%D0%BE%D0%B3%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F%20%D0%B4%D0%BB%D1%8F%20'%D0%90%D0%BB%D0%B5%D0%BA%D1%81%D0%B0%D0%BD%D0%B4%D1%80%D0%B8%D1%82'.drawio 



Вопрос специфический, с учетом того, что ранее я упоминал ELT стек и у нас относительно легаси инфраструктура, то можно выбрать Logstash для сбора логов, но он довольно тяжелый по ресурсам в отличии от того же Fluent Bit.
Но, пускай основым инструментом логирования будет выступать Logstash + Beats (компонент ELK стека, который позволяет использовать легковесных агентов для сбора данных из различных источников) для снижения нагрузки.
Итого:
    - Сбор логов: Logstash
    - Хранение логов: Elasticsearch (TS DB хранилище)
    - Визуализация логов: Kibana раз используем Elasticsearch
    - Алертинг: Kibana Alerting (из коробки позволяет отравлять email, сообщения в slack, можно прикрутить свою интеграцию через вебхуки)

3.1. Политика безопасности для логов:
    - Маскируем чувствительные данные (личные данные клиентов (email, номера телефонов))
    - Используем TLS 1.3 для передачи логов 
    - Можно настроить X-Pack Security в Elasticsearch, т.к. в состоянии покоя данные не шифруются
    - Доступ к логам должен быть только у команды разработки (можно использовать VPN)
    - Логируем запросы к логам, прошу прощение за тавтологию :)

3.2. Политика хранения логов 

    - RabbiqMQ. 1-2 недели. Т.к. основной пул проблем с потерей заказов обнаруживается довольно быстро.
    - MES. 1-2 месяца, но может зависеть от цикла производства ювелирных изделий
    - API для партнеров. 1-2 месяца, но может зависеть от требований в рамках партнерских соглашений/договоров
    - CRM. 1-2 месяца, может зависеть от гарантийных обязательств перед клиентом
    - Отдельно хочу отметить, что хранение персональных данных по ФЗ-152 (в Россиии) регламентирует удаление этих самых данных через 1 месяц после того как цель использования данных достигнута (чтобы это не значило :)

*Для каждой системы лучше выделить отдельный индекс в Elasticsearch. Т.к. индексы шардируются автоматически и каждый ииндекс будет хранить логи из одного источника (например rabbitmq-<YYYY-MM-DD>)

3.3. Превращение системы сбора логов в систему анализа логов

    - После внедрения Logstash и ELK можно реализовать рекомендательный чек-лист для исследования инцидентов
    - Настроить различные визуализации логов в Kibana
    - При помощи Kibana Alerting можно реализовать отправку сообщений о ERROR и FATAL по email и через вебхук запрограммировать интеграцию, например в Telegram-бот 
    - Также можно реализовать ежедневные и еженедельные автогенерируемые отчеты о критических ошибках.
