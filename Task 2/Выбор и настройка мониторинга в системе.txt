Ключевые проблемы без мониторинга:

- Условная "слепота" в B2B-канале: часть заказов (через API) не видны в Яндекс.Метрике

- Невозможность диагностики сбоев: Потеря заказов в интеграциях обнаруживается только через жалобы

- Простои производства: Операторы простаивают из-за медленного MES, но причины неизвестны

- Репутационные риски: Клиенты и партнеры теряют доверие из-за просрочек

Соответственнно данные проблемы являются мотивацией к внедрению мониторинга в "Александрит"

1. Мотивация

1.1. Предотвращение потерь денег

    - Каждый потерянный B2B-контракт = определенный процент упущенной выручки

    - Мониторинг RabbitMQ DLQ предотвратит большую часть  таких потерь

1.2. Увеличение скорости производства

    - Снижение времени простоя операторов через оптимизацию MES

1.3. Защита репутации

    - Раннее обнаружение сбоев API снизит жалобы партнеров

1.4. Обоснование инвестиций

    Данные о загрузке CPU/БД покажут, куда можно использовать плановый бюджет на инфраструктуру


2. Выбор подхода к мониторингу

2.1. RabbitMQ.	Лучше использовать RED подход, т.к. RabbitMQ — это канал доставки заказов, а не пассивная инфраструктура.
Фокус: 	Бизнес-логика доставки
Ошибки: Недоставленные/зависшие сообщения
Метрики: 
    - Number of dead-letter-exchange letters. Для обнаружения потерянных заказов
    - Number of message in flight. Для возможности контроля задержек в интеграциях
Ярлыки: queue_name, message_type, error_type     

2.2. Онлайн-магазин API. Подходит RED, т.е. он эффективен для сервисов, которые управляются запросами.
Фокус: 	Выявление аномальной нагрузки
Метрики: 
    - Number of requests (RPS) for shop API. Для получения объема трафика
    - Response time (latency) for shop API. Для определения "узких" мест в производительности API
    - CPU % for shop API. Для отслеживания ресурсов процессора на выполнение операций API интернет магазина
    - Memory Utilisation for shop API. Отслеживания ресурсов RAM для исключения memoryleak на выполнениях операций API интернет магазина
    - Number of HTTP 500 for shop API. Для определения ошибок создания заказа
    - Kb tranferred (received) for shop API. Мониторинг объема загружаемых 3D-моделей
Ярлыки: endpoint, error_code, file_size, file_type

2.3. CRM API. RED подход (обоснование выбора подхода аналогично п.2.2)
Фокус: 	Выявление аномальной нагрузки в работе CRM
Метрики: 
    - Number of requests (RPS) for CRM API. Для получения объема трафика/ активности работы менеджеров
    - Response time (latency) for CRM API. Для улучшениия скорости работы продавцов
    - CPU % for CRM API. Для отслеживания ресурсов процессора на выполнение операций CRM API
    - Memory Utilisation for CRM API. Отслеживания ресурсов RAM для исключения memoryleak на выполнениях операций API CRM
    - Number of HTTP 500 for CRM API. Для определения ошибок подтверждения заказа
    - Дополнительно можно ввести около бизнесовую метрику количества подтвержденных заказов в час - Orders approved/hour
Ярлыки: endpoint, error_code, order_type

2.4.  MES API. RED подход (обоснование выбора подхода аналогично п.2.2)
Фокус: 	Выявление аномальной нагрузки в работе MES сервиса
Метрики: 
    - Number of requests (RPS) for MES API. Для получения информациии о нагрузке на сервис
    - Response time (latency) for MES API. Для улучшениия скорости работы операторов
    - CPU % for MES API. Для отслеживания ресурсов процессора на выполнение операций MES API    
    - Memory Utilisation for MES API. Отслеживания ресурсов RAM для исключения memoryleak на выполнениях операций API MES
    - Number of HTTP 500 for MES API. Для определения ошибок в MES
    - Kb provided (sent) for MES API. Отслеживание объема передаваемых 3D-моделей на производство
Ярлыки: endpoint, error_code, order_type

2.5. БД. USE подход. USE лучше всего работает с ресурсами, производительность которых снижается при интенсивном использовании. БД как раз можно причислить к таким ресурсам.
Фокус: 	Выявление проблем при работе с Shop DB и MES DB.
Метрики: 
    - Memory Utilisation for MES db. Для получения информациии о зависаниях в момент получения информациии в дашбордах
    - Number of connections for MES db. Для выявления риска отказа базы данных при пиковых нагрузках.
    - Size of MES db instance. Для планирования увеличения размера MES DB
    - Size of shop db instance. Для планирования увеличения размера Shop DB 


2.6. S3 хранилище 3D-моделей. USE подход
Фокус: 	Выявление проблем при работе с Shop DB и MES DB.
Метрики: 
    - Size of S3 storage. Для анализа размера 3d files storage и контроля затрат на хранение 3D-моделей.



3. План действий

Необходимо произвести настройку инфраструктуры мониторинга, а именно:

3.1. Развертывание time-series БД
    - Оформить Yandex Managed Service for Prometheus в Yandex Cloud
    - Конфигурация: 2-3 ноды с 16GB RAM, 100GB SSD (масштабируемый)
    - Настроить ежедневные снепшоты хранилища
3.2. Визуализация     
    - Развернуть Grafana (можно на отдельной VM)
    - Интегрировать с Prometheus

Далее необходиимо настраивать интеграцию с источниками метрик

3.3. RabbitMQ. 
    - Установить rabbitmq_prometheus plugin
    - Настроить сбор метрик из перечня п. 2.1.
3.4. API Интернет магазин, CRM и MES
    - Доработать логику для отправки данных в prometheus

3.5. Базы данных
    - Настроить Postgres Exporter для всех инстансов БД, чтобы Prometheus мог забирать метрики по БД. 

Далее нужно отработать правила алертинга по критическим метрикам (Number of dead-letter-exchange letters, Response time (latency)  и т.п.)


4. Дополнительное задание. 
Показатели насыщенности (Saturation) и пороговые действия
Насыщенность — показатель заполненности ресурса с точки зрения его способности обслуживать работу (очереди, задержки, конкуренция). Ключевые показатели для "Александрита" на мой взгляд:

    - Базы данных: Очередь запросов к БД. 
    Большое количество запросов может блокировать обновления статусов заказов, из-за чего операторы не смогут вовремя получать актуальные статусы и принимать заказы в работу.
    При привышении определенного порога запросов можно реализовать автомасштабирование дополнительнной реплики БД на чтение, отправлять тикет для Тимлида/Продакта с высооким приоритетеом.

    - RabbitMQ: Время в очереди
    При длительном расчете стоимости на MES объект в очереди может долго не быть разобран из-за чего возможен рииск отмены заказа клиентом.
    Если существуют сообщения с высоким временем нахождения в очереди, то можно отправлять уведомления на разработчика ии автоматически создавать инциидент в системе таск-трекера.

    - CPU: Saturation Load.
    Используется для проверки загрузки процессора хоста, и если средняя загрузка составляет более 75 % или пиковая – более 90 %, значит, наблюдается нехватка ресурсов CPU 

    -Дисковый I/O: Задержка операций (Disk write latency seconds)
    Мера производительности дискового устройства, которая показывает, сколько времени в секундах требуется для завершения записи данных на диск. 
    Более низкое время задержки записи означает более быструю и эффективную работу диска. 
    При критичном пороге можно автоматически запускать скрипты на очистку кеша баз данных, для S3 хранилища можно выбрать логику очистки временных файлов старше N-дней.
